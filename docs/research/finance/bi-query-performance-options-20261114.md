# 财务 BI 查询提速：成熟方案与项目选型

调研日期：2026-11-14（北京时间）。性质：调研与决策材料，调研阶段未修改应用、迁移、Redis 配置或生产数据。用户随后将 B 路线五步设为持续实施目标，已开始第一阶段索引与观测计划；尚未证明的精准补算/尾差协议仍须完成设计与实验门槛。以下将官方资料、项目实测和建议分别标明。

## 建议

建议选择方案 B：分阶段完善现有 MySQL 查询事实、增量汇总和版本化 Redis，先把已提出的单索引优化纳入第一阶段，再以真实负载决定更细的补算粒度。专用分析数据库作为后续扩展选项。此建议是结合项目现状作出的工程判断，不是厂商的性能保证。

继续采用用户已选的新鲜度：结果包含查询数据库快照内已提交的变化。平台尚未同步的数据仍须注明覆盖范围；不能把缓存、查询或投影完成解释为上游数据齐全。

## 1. 行业中可复用的成熟方法

官方资料提供的是不同负载下的设计方法，没有统一的“BI 一定小于几秒”承诺。

可以把成熟链路理解为三种材料：原始账单是凭证；查询事实与汇总是持续维护的报表底稿；Redis 保存某一完整版本、某一查询条件的答案。底稿降低第一次计算的工作量，Redis 降低重复取同一答案的工作量。两者需要配合，不能用缓存容量代替查询模型设计。

| 方法 | 通俗理解 | 适用价值与边界 | 资料 |
| --- | --- | --- | --- |
| 索引、SQL 和执行计划 | 把档案目录按查找顺序排列 | 可消除无必要排序、宽行扫描；结果取决于实际条件及计划，仍须承担必要的统计计算 | S1 |
| 事实与维度分层、预聚合 | 把“账单原件”和“报表统计底稿”分别整理 | 常用汇总从较小数据集读取；复杂指标、口径变化和明细下钻仍需专门处理 | S2、S3 |
| 按变化更新物化结果 | 某笔订单变化，只重做它影响的统计 | 降低重复计算；要正确处理修改、删除、乱序、重复、历史回补和跨月移动 | S4、S5 |
| 版本化结果缓存 | 复用相同条件、相同版本的已算答案 | 适合重复查询；过期时间本身不能保证与业务库一致 | S6 |
| 独立查询模型与负载隔离 | 业务写入与报表查询使用各自合适的结构 | 可先在同一数据库使用不同模型，也可分到独立存储；跨库增加同步与一致性成本 | S7、S8 |
| 列式分析库及物化视图 | 使用适合大批量统计的专用账房 | 提供额外的汇总与刷新机制；MySQL 到分析库的同步和财务语义仍需验证 | S9、S10 |
| 按尾部延迟验收 | 看慢请求和错误，而不只看平均速度 | 分开观测延迟、流量、错误、资源饱和；冷查询与持续导入必须覆盖 | S11 |

CQRS 的基础形式允许读写模型保留在同一数据库，并不必然要求增加消息中间件或迁移数据库。本文方案 B 优先采用这一层次。相关的同库原子更新协议仍需设计和验证。

## 2. 项目已具备哪些基础

已有按页接口、稳定分页、窄索引、压缩缓存、同进程相同请求合并、原币事实投影、变更事件、修订围栏、后台租约及失败回滚。不能把本项目描述成“完全没有 BI 架构”。

真正缺口是：这些能力尚未在持续变化的真实负载下，形成稳定的低延迟完整查询链路。原始来源、订单成本、首次结算、历史 FX 等业务语义复杂，新工具不能直接替代现有规则。

| 能力 | 当前项目 | 差距与优先级 |
| --- | --- | --- |
| 索引及 SQL | 已多轮优化；V159 首笔结算专用索引已在实际计划中消除该关联的排序，订单选行和费用精确计数仍慢 | 保留已验证收益，继续处理剩余慢段；局部优先，不能据此承诺全系统达标 |
| 按页、按需加载 | 已拆专页，成本子页按需加载；默认贴单导航已并行 | 基础较完整，继续减少无关请求并保持取消和同条件边界 |
| 面向查询的事实与汇总 | 已有成本/贴单/广告事实表及月份 JSON 投影 | 复用现有事实，补齐首次结算等查询身份；评估较细的汇总存储，减少重复关联和整月正文处理 |
| 精准增量 | 已有版本化脏日、内部基线与事件消费 | 来源依赖及店铺身份尚不够细；更细草案未通过真实服务能力门槛，不能直接假定它会追平 |
| 一致性与新鲜度 | 专页 READY/版本/相关事件校验；未追平回源 | 保护正确性，但回源昂贵。通用缓存仍有短时旧结果复用规则，须与目标页面的新鲜度契约统一 |
| Redis 治理 | 共享实例，按范围限条数、限对象大小并设 TTL | 无独立内存上限，登录会话等共用；先补按业务的命中与回源统计，按实测决定是否分离缓存资源 |
| 负载隔离 | 业务写入、后台补算和查询共用现有数据库资源 | 需要工作预算、查询与后台负载观测；增加副本只分摊负载，不能自动降低单条复杂 SQL 成本 |
| 服务质量验证 | 已有隔离库、真实同快照对照和部分浏览器样本 | 各页冷查询、并发、持续导入与长期尾延迟尚未全部验收；缺少已经验收的按页 Redis 命中率和回源分段看板 |

这里不赋予“成熟度百分数”，因为各能力权重和业务负载没有统一行业评分。以上是可对照源码及验收记录的能力差距。

以下是既有验收样本，不是本次重新压测或未来保证。来源见文末项目证据。

| --- | --- | --- |
| 广告分析 | 30 个混合完整样本最大 3.992 秒 | 这组样本通过；不是所有并发、所有条件的长期保证 |
| 成本完整刷新 | 4.533 / 4.682 / 4.809 秒 | 已接近预算上限 |
| 成本导航进入 | 5.256 秒 | 该样本还需减少 0.256 秒 |
| 整站重载进入成本页 | 5.829 秒 | 该样本还需减少 0.829 秒，包含启动和页面链路 |
| 订单默认页 | 单次 8.616 秒 | 该样本还需减少 3.616 秒 |
| 费用页 | 27.440 秒仍忙，82.091 秒观察已完成 | 精确完成时刻未知，属于结构性慢链路，不能当作精确 82.091 秒 |

成本只读分段调用 4.423 秒，其中首笔结算汇总 3.835 秒，约占 87%；三个来源计数合计 0.447 秒、50 行明细 0.024 秒。执行计划估算约 159,220 个候选订单，不能把估算值当作实际循环计数。

最初提出将既有索引的 id 显式放在 record_date 后，但隔离实验否定了单独调整顺序即可消除排序的假设。后续实际验证的方案是保留原索引，新增 11 列首笔专用索引，并在关联查询排序中显式列出调用内固定的前缀；146 项相关回归及独立审查通过。随后 V159 已受控生效，具体回执见常驻性能与上线说明；此前变慢或超时的 SQL/索引候选均未上线。

V159 后两轮同一真实只读 RR 的原/新实际查询为 4.672→3.340 秒、3.799→3.078 秒（第二轮执行次序反转），四项汇总一致，新路径消除 r0 排序且仍为覆盖读取。两轮均值减少约 1.027 秒（24.2%）；不是长期性能或整页保证。新的完整刷新仍有 9.640 秒超标样本，随后 4.051/3.863 秒、重载 4.342 秒、菜单进入 4.454 秒；分组筛选 18.611 秒时仍忙并被后续动作替代，完成时间未知。后续下一页触发完整重读，不计作纯分页成绩。全部目标仍未验收完成。

贴单完整 workspace 的只读可重复读边界随后也已受控生效。该阶段六个实际 UI 样本为：完整刷新 3.816 秒；服装组筛选 30.218 秒且出现错误反馈；另一个后续观测窗口的全部/服装组/纯分页/恢复分别为 3.856/4.569/1.108/4.311 秒。错误反馈的完整文字及该失败请求的恢复完成时刻未留存；后续数据库等待采样在失败之后开始，不能用它解释这次慢请求。不得只摘取后续快速样本宣称五秒目标已完成。证据：本机 `labels-rr-actual-ui-20261114.json`、`label-ui-waits-rr-observation.json`。

## 4. Redis 应该如何参与整体方案

本次之前的只读核对：Redis 实例 used_memory 采样约 2.47 MiB，无固定 maxmemory/容器内存上限，策略 noeviction，AOF everysec；与登录会话等共用。某一瞬间有 5 份通用结果和 1 份事实缓存、没有专页页缓存键。这是瞬时库存，不能计算 BI 命中率，也不能据此断定缓存从未生效。

2026-11-14 17:19（北京时间）再次只读复核：`used_memory=2408424`，约 2.30 MiB，RSS 12.81 MiB；`maxmemory=0`、容器内存限制为 0、`noeviction`、AOF `everysec` 均保持，累计淘汰数为 0。这里的 used_memory 是 Redis 实例内存，不等于 BI 缓存正文体积；全实例累计 hits/misses 也不能当作财务 BI 的命中率。当前没有缓存容量不足的证据，因此不将扩容 Redis 排在查询模型改造之前。

19:41:26（北京时间）的新一次只读元数据核对：`used_memory=2389944`，约 2.28 MiB，RSS 13,598,720 字节；Redis 8.8.1，`maxmemory=0`、容器内存限制 0、`noeviction`、累计淘汰 0、AOF `everysec` 及持久化状态正常。仍是全实例瞬时采样，未输出业务正文或凭据，也没有调整配置。小型回执位于本机 `redis-research-read-20261114-194126.json`。

当前月度贴单接口直接查询数据库，增加 Redis 内存不会自动把它接入缓存。专页只有严格版本可用时进入页缓存，持续变化下 PENDING 回源也限制了缓存收益。

建议的 Redis 职责：保存相同完整查询版本的结果；键覆盖组织/权限范围、筛选、页码、币种、FX、首次结算等口径版本；当前个人设置继续单独读取。数据变更先由一致性协议确认版本，不只等待 TTL。保留对象大小、条数、超时和失败回源边界；监控时将财务命中率与会话/任务读写区分。

共享实例中的登录和任务状态需要保留。Redis 官方建议将持久业务键与需要淘汰的缓存按负载分离；若采用隔离缓存实例，才单独评估内存上限和淘汰策略。当前证据不足以指定应分配几 GiB，也不支持直接给共享实例启用淘汰全部键的策略。

| 调整 | 能解决的问题 | 对本项目的实际边界 |
| --- | --- | --- |
| 直接增加 Redis 内存 | 已有缓存因容量不足而无法保留 | 目前没有容量不足证据；不会自动加速月度贴单直查、首次计算或精确计数 |
| 只延长 TTL | 减少同条件重复计算 | 不能据此证明包含查询快照内已提交变化，不符合把旧结果视为当前结果的做法 |
| 完整版本作为缓存键的一部分 | 安全复用相同口径和已覆盖版本 | 必须先解决后台维护覆盖；组织、权限、筛选、币种及规则版本均不能遗漏 |
| 按完整查询版本合并同时到来的相同计算 | 减少同一答案被多次并行计算 | 已有进程内合并；多个进程是否需要额外协调，应以实际部署和观测决定 |
| 财务缓存资源隔离、命中与回源监控 | 分清缓存收益，避免与登录/任务状态争抢资源 | 是运维治理选项；不能替代查询事实和增量维护，也不是开始 B 路线的前置条件 |

客户端配置的 3 秒 Redis 超时也应纳入故障场景的整页预算；尚未完成的故障演练不能按正常命中时间推断。

## 5. 三条路线

| 决策 | 具体内容 | 覆盖范围 | 开发/运维投入 | 主要限制 |
| --- | --- | --- | --- | --- |
| A：局部优化 | 调整首笔结算索引、继续定位最慢 SQL、完善缓存观测及加载链路 | 成本页及个别慢查询 | 较小；仍有索引迁移与压测成本 | 很难单靠它解决费用/订单在持续同步下的整体问题 |
| B：现有架构分层完善（推荐） | A + 复用/补齐查询事实 + 受影响范围的幂等更新 + 小粒度汇总 + 版本化 Redis + 严格覆盖验证 | 以全部目标页面的首次加载和筛选为目标 | 中等；需新增派生结构、回填和并发校验；优先复用既有事件及 MySQL | 必须证明补算能追上变化；复杂变更可能扩大范围，性能尚未得到保证 |
| C：独立分析库 | 设计查询事实和指标模型；将 MySQL 变化通过 CDC 同步到 Doris/ClickHouse 等候选，BI 读分析模型 | 大范围、多维、高并发分析 | 最大；增加数据库、同步、存储、监控和恢复工作 | 同步延迟、历史更正、删除和维度变更仍需处理；不能自动满足严格最新快照 |

投入为相对工程判断，不是工期、云资源报价或性能承诺。是否增加独立 Redis、读副本或分析集群，须由并发和资源实测决定，不预设必须扩容。

### 推荐 B 的具体含义

1. 首先完成 A 中的索引验证、实际执行计划及按页分段观测。
2. 按实际查询明确最小事实粒度，复用已有订单成本、贴单与广告事实，补齐反复查询的首次结算身份。再形成按店铺/业务日期/必要分类的汇总；未知金额和精确计数必须有对应状态或计数，不能只存金额和总和。
3. 变更先与业务提交一起登记，重复工作可安全重试。修改或删除替换原事实，首次结算跨月移动要同时覆盖旧、新归属；分组、规则及 FX 变化按真实依赖扩大范围。
4. 先验证小粒度补算是否在真实导入速率下持续追平；同一店铺/日期/依赖的通知可合并。只把“公司日”改成“店铺日”并不能证明服务能力够用。
5. 若正常可控的小范围尾差仍阻碍查询，可单独评估“已验证基线 + 同快照精确补齐未覆盖变化”的读取协议；覆盖完整后才输出结果。它是新的候选设计，不是已获批草案或现有能力。无法完整补齐时保留权威回源，不能把旧基线标成最新。
6. Redis 缓存最终完整版本；前端继续按页读取、并行独立请求、轻量更新任务状态，避免后台心跳触发整页重算。

示例：某店某日的一笔订单成本由 10 元改为 12 元，优先更新这一订单及它影响的统计。若该变化同时移动首次结算月份，必须处理两个月的归属；不能将所有变化都当成简单加减。此示例为说明规则，非真实业务金额。

候选链路：业务原始记录 → 同事务变更登记 → 查询事实与受影响汇总 → 查询快照覆盖校验/必要的精确补齐 → 版本化 Redis → 页面。基线是内部计算材料，返回结果仍要满足用户的新鲜度规则。

## 6. 为什么不直接决定上分析库或读副本

异步 MySQL 副本及 CDC 链路会增加可见性延迟；需要同步位点/已覆盖事务证明、等待或主库路径，不能单凭“复制已开启”判断查询包含最新提交。分析库内部的同步物化视图也不能消除上游 MySQL 到分析库的延迟。

ClickHouse 官方资料特别说明：增量物化视图的 JOIN 右表变化不会自动触发该视图重算。因此店铺分组、成本目录等维度改变后的旧汇总刷新必须设计，不能只配置 INSERT 同步。Doris 的同步/异步视图则有不同刷新与一致性规则；选择前需要用本项目完整语义验证。

如果 B 的受控试验表明冷查询或补算吞吐仍不满足目标，或者真实并发压测持续影响交易和同步，再比较 C 的候选并作影子对账。当前没有跨引擎同数据、同语义、同并发的实测，不能预测换库后一定快多少倍。

### 如何作下一步选择

以下是工程建议，不是厂商性能承诺或新增上线授权：

- 若只准备处理个别慢查询、接受订单和费用页仍可能超过五秒，选择 A。它也是 B 的必要基础；已生效的 V159 属于这一层，不能重复计算为待上线成果。
- 若继续要求当前财务口径、查询快照内已提交变化和全部目标页面五秒内完整显示，优先继续已选择的 B。它先复用当前 MySQL 与事实数据，新增结构主要是可重建的查询底稿；成本集中在依赖完整性、历史更正和并发验证。
- 若同语义、冷缓存及持续导入实验表明 B 仍缺乏足够处理能力，或真实多用户负载持续影响业务写入，再为 C 做独立分析库试验。先验证最慢查询和更正/删除/维度变化，再决定产品和资源；异步同步延迟必须另有可见性证明或权威回源。

当前与 B 的主要距离，是首次结算关系、独立精确计数、金额贡献及广告重叠依赖尚未形成完整且已验收的维护/查询链路，不是缺少一个 Redis 开关。首个事实原型的表、事务登记、初始化/升级及 RR→CAS 工作器已完成本地隔离验证和独立审查；真实贴单消费者仍在隔离验证及审查修复中。容量、影子验证和生产激活尚未完成，生产未安装这些事实表、触发器或工作器。独立精确计数、金额贡献及完整版本 Redis 仍是后续范围，不能把原型测试通过当作全系统已提速。

为便于选择，下一阶段每次只验收一个可观察结果：首笔关系能正确复用；费用/订单能快速取得精确总数和目标页；变更只更新真实受影响范围且能追上正常写入；最后让 Redis 安全复用完整版本。跨月首笔变化、旧记录删除和账户级广告不能一律按店铺日做简单加减。

## 7. 决策后如何验收

- 保留完整新鲜度、权限、首次结算、归属月、刷单排除、广告重叠、历史 FX、未知及精度语义。
- 代表性默认加载、月份/店铺/分组/币种筛选、分页及冷 Redis 情况，主表和关键汇总完整、无错误才算完成。
- 正常同步及实际导入持续运行，记录变更到达、合并后的工作量、处理吞吐、落后时间及回源比例；不能暂停业务取得成绩。
- 逐场景扩充完整样本，保留所有超五秒、超时及未知完成时间；同时观察 P50/P95/P99 与最大值。有限样本不能证明长期 P99，P95 也不能替代用户要求的五秒样本验收。
- 索引、事实维护、增量和页面的结果分别与独立权威计算在同快照对照。派生数据可重建，迁移和源码分阶段维护、审查及回退。
