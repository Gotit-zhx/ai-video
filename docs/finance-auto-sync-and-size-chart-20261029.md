# 财务自动同步与商品尺码表修复

日期：2026-10-29

## 财务

- 线上 `FinanceController` 未包含 Java 参数名元数据，原来未命名的 `@PathVariable` 导致配置请求在进入保存方法之前失败。明确填写全部路径参数和标量上传参数名称，不再依赖编译参数。
- 财务店铺成功授权后，在同一事务中保存授权、开启同步并建立通道。Shopee 五个通道，TikTok Shop 六个通道。
- 手动开启同步和授权使用同一通道初始化逻辑。重新授权保留记录、原授权所有者、同步断点、历史覆盖范围以及仍有效的工作租约。
- 同公司重复授权继续复用原店铺。只有明确重新授权的店铺才按本次选择变更分组。
- 不批量开启此前手动暂停的店铺。仅补开本次因配置接口错误而未启动的 SOFTRY-PH、SOFTRY-TH；两家实时订单通道均已成功运行。

验证：38 项 FinanceTest（包括真实 MockMvc 路径绑定与跨站拒绝），12 项独立 MySQL 数据库场景全部通过。数据库场景包含授权、重复授权、分组、凭据隔离、断点和租约保护、并行工作者隔离。临时测试库与账户已删除。

## 商品上传

- TikTok 上传界面接收补录尺码表，批量请求传递选中图片；后台按公司校验归档图片，再传给官方尺码表接口。
- 提取商品原始属性内的完整尺寸表，严格检查测量列、单位和数值。不使用颜色款式图冒充尺码表，不生成缺失尺寸。
- 安全失败项重新提交时生成新的幂等键，保留原选项。已经创建、结果不确定、运行中的工作流不重放。
- 本次核对 11 次失败，涉及 Sweet Me 店铺的 4 款商品，均未跨过官方商品创建边界；原始属性中均有五行尺寸测量。
- 使用四个独立恢复工作流，保留旧失败工作流和审计记录。原失败审计有幂等缓存，不能仅将旧流程改回待执行。
- 恢复前在回滚事务中检查原店铺、商品版本、原始尺寸、图片任务和既有发布结果。恢复脚本固定限定这四个商品和原店铺，并利用唯一目标键防重复。

验证：119 项前端测试及尺码表、TikTok 发布、原始尺码保护、Shopee 尺码提取的针对性 Java 测试通过。正式发布采用准确线上 JAR/静态资源覆盖，保留其他类、数据库版本 135、服务配置和业务数据；验证静态文件原始及 gzip 内容、服务健康、未登录访问保护。

发布产物：`product-size-chart-repair-20261029`、`finance-auto-sync-20261029`。发布过程中发现临时静态文件权限为 0600 导致 nginx 无法读取；发布检查触发回滚，修正为 0644，并以 nginx 工作用户确认可读后完成正式发布。
