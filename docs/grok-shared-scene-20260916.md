## 流程和调用

- 每个来源商品准备一次 `SCENE_BACKGROUND`：优先同公司启用的 Grok，无可用 Grok 时选择默认图片模型；不修改公司的默认模型。
- 场景生成只补全空背景，不重画服装或印花。同商品的全部款式、SKU 颜色与辅助视角共用背景。
- 缓存绑定提取图、模板正面构图图、模型指纹、提示词和算法版本。同输入已归档背景可跨后续批次复用；不能仅按颜色名称或“背景看起来一样”跨来源混用。
- 多来源批次保守预留每来源一次背景调用，实际缓存命中不消耗模型调用；已有印花复用仍不新增提取或裂变调用。
- 透明印花仍由 IMG2.0 生成。场景请求每次只允许一次上游 POST，未知结果不会盲重试或切模型，下载失败只恢复下载；旧冻结任务保留原策略。
- 本地合成保留衣服与印花内区像素，只在窄边缘去除原白底混色；检测到轮廓外图案会停止，避免更换背景时静默丢失图案。正反左右几何遮罩在付费前校验。

## 验证

- 真实 Grok：1 次 POST，HTTP 200，生成 18.881 秒，含下载 19.880 秒。参考第八次测试的实际提取图，保留黑网椅、杂志架、地砖，移除旧衣服和印花；结果已归档缓存，没有再次生成背景。
- 用同一背景和同一已归档透明印花，按真实模板 UV 合成白色、黑色两款。未新增印花或成品图模型调用。
- 后端 151 项通过，包含 3 项真实 MySQL 缓存归档、幂等与租约测试，0 失败/错误/跳过；前端 120 项通过；runtime 128 项通过。
- 实图发现白底边界 2044 像素中有 4 个蓝色杂点，原换色检测使用通道极值导致误拒绝。现用 1%–99% 分位差，仍拒绝真实渐变、复杂背景和裁切衣服，新增 3 项回归。
- QA 浏览器验证生成新印花与复用印花的说明、新缓存版本及来源隔离。未提交新商品或覆盖历史批次。应用健康为 UP，正式与 QA JAR SHA 相同。

## 边界
