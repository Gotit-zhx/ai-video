## 调度故障、修复与业务边界

首次维护代码使用 `setTaskDecorator` 跳过整个 `RunnableScheduledFuture.run`，使维护期间首次触发的周期任务失去再次排队。健康、鉴权、静态资源和维护协议测试均可通过，却不能证明上传轮询已恢复。这是一期验收遗漏，不能归因于用户的原有任务或未清除的维护标记。

v7 把门控移到业务回调，保留 Future 生命周期。真实 Spring fixedDelay、fixedRate、Trigger 三项回归在旧实现失败、修复后通过；另覆盖真实 `@Scheduled(initialDelay)` 在维护期启动后的恢复。定向 Java 回归 85 项；运维测试 55 项、CI 策略测试 30 项。排空 SQL 的两项边界回归使用 SQLite 执行谓词，不将其描述为生产 MySQL 测试。完整候选另有隔离 MySQL 与真实镜像验证。

热修复验收确认原两条工作流自然恢复：原图预处理 19/19 成功，截图对应九图流程到 READY 9/9 后进入 PUBLISH；另一七图流程在交接时为 READY 4/7 并继续生成。没有重建工作流、人工付费调用或改写业务记录；**未宣称全部平台上传已完成**。业务详细记录见[上传调度恢复](../commerce/upload-scheduler-recovery-20261107.md)，公开补充回执为 v7 Release 的 `upload-scheduler-acceptance-20bb157.json`。

排空只放行从未领取的持久积压：`PENDING/QUEUED`、`attempt_count=0`、两个锁字段为空、`publication_attempted=false`。既往领取、任何锁（含过期锁）、正在运行或跨外部创建边界仍阻止切换；不能修改这些字段获得发布窗口。后续广告 .9 必须重新核对现场业务安全点。

## 缺陷版本的回滚资格隔离

v3/v4/v5 共用缺陷后端 manifest `sha256:4070261f788e2e1521dad431e78609c98dfce2f98bb9c5060af334f7ca3716d7`。在确认 v7 活动、配置与 schema 未漂移、无未完成运维且无容器引用该后端后，按双锁顺序完成：

1. 保存路径、归属、原 manifest 和 `verified.json` 的 SHA-256 计划。
2. 将三份 root 所有的验证文件原字节移至 `/opt/heyi/ops/quarantine/20261107-upload-scheduler/<版本>/verified.json`，附 `reason.json`。

原始签名仍是历史来源证据，撤销的是部署资格。原清单、源码包、镜像、已发布回执和前端仍引用的配置均保留；未删除任何业务数据或镜像。旧版本不能通过要求“当前生产 HEAD”的 stage 校验重新预取，禁止人工复制隔离文件重新启用。

目前只有 v7 一组修复后的受管应用组合，v8 复用它。旧体系 `finance-advertising-20261106` 与 `finance-cold-queries-20261106` / `brush-source-summary-20261106` 两组保留作独立兼容性审查后的人工恢复候选。不能将保留历史列表描述为两个健康的自动回滚镜像。
