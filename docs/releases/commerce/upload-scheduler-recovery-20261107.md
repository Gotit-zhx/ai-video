# 上传与主图定时工作器恢复 · 2026-11-07

候选分支：`hotfix/2026.11.7.7-upload-scheduler`，基于正式 `v2026.11.7.5`。此记录保存诊断与候选验证，正式激活状态以同版本 GitHub Release 和 `heyi-ops` 回执为准。

## 现场与原因

11 月 7 日约 15:09（北京时间），正式服务健康、维护门控关闭，但两条新上传工作流一直为 `PENDING / IMAGES`，领取次数和后端重试次数均为 0、没有租约，且符合领取 SQL 条件。截图中的九图模板与其中一条工作流匹配；该工作流没有建立新的风格图任务。页面“已自动重试”来自前端进度同步，不能解释为已重复调用模型。

`MaintenanceScheduling` 原来使用 `ThreadPoolTaskScheduler.setTaskDecorator` 包住底层 `RunnableScheduledFuture`。维护期间不调用整个 Future，导致其自身的再次排队也不执行。应用在维护标记存在时启动，会让首次触发的固定延迟、固定频率及 Trigger 任务停止，移除标记也不能恢复。

## 修复与验证

维护检查移到实际业务回调内部，保留定时 Future/Trigger 的执行、再次排队、取消及错误处理。调度仍使用原有单线程；维护期间不领取业务，已接受工作继续按原计数排空。未修改数据库结构、工作流数据、模型请求身份、发布审计或同步检查点。

旧行为的三项真实 Spring 调度测试均复现维护结束后无法继续。修复后，固定延迟、固定频率、Trigger 及真实 `@Scheduled(initialDelay=...)` 启动维护场景通过；维护与商品上传定向回归共 85 项，0 失败、0 错误、0 跳过。

分支另包含已验证的 CI 基础修复：隔离 MySQL 使用认证 TCP 查询确认最终实例就绪；有组件变化时，在已认证步骤预取并核对复用的私有镜像。广告连接候选未进入此热修复。

## 激活与验收边界

必须通过完整 CI、同一候选的真实镜像冒烟及来源证明，经 Gitflow 合并/标签和统一运维入口上线。生产验收核对原有队列领取次数推进、逐图状态变化及外部发布边界，不清队列、不重放未知平台创建、不发起新的测试付费生图。模型最终成功与平台上传成功需分别记录，不能用调度恢复替代整条业务完成。
