# 2026-10-16：新来信被动跟进修复

> 历史发布记录；镜像、测试与“当前/最新”均指记录当时。 当前入口见[业务说明](../../business/README.md)与[运维指南](../../guides/operations.md)。

本次只修改招聘工作台隔离分支，保留原账号、登录资料、请求账本和不确定写操作记录。

## 已确认的问题

- 原客户端消息通知通常没有职位编号。旧分支对尚未入队的会话直接标记完成，没有查询该候选人的官方职位绑定。
- 原生列表和宿主允许恢复最近一小时的消息，Python 入队只接受最近三分钟，启动期间的较早来信会丢失。
- 历史补处理和职位状态刷新把其他通道的最近请求当作自己的冷却起点，持续收件会推迟检查。职位状态过期时会暂停沟通，即使官方职位仍开放。

## 实现

- 无职位编号的来信先逐条查询官方会话详情，只在精确匹配已启用且开放的职位后加入消息核实队列；不从候选人文本、当前页面或第一个职位猜测归属。
- 部分详情缺失时保留待核实提示并缓慢重试；平台风险或会话错误继续停止操作。
- 一次性恢复本账号最近七天被旧逻辑丢弃的无职位提示，仅恢复读取，不重置已发送、索取、入库和不确定操作记录。
- 启动来信时间窗口与宿主一致；已入队的会话读取优先于普通附件历史扫描。
- 历史补处理使用自己的持久执行时间；职位刷新使用已有五分钟持久冷却，并继续受共享配额限制。
- 保留每小时 500 次共享请求上限、每日 150 次招呼限制、历史缓慢补收、关闭职位禁止新沟通和已发附件继续入库。
- 修复 Windows 回归用例未关闭 SQLite 连接造成的临时文件清理失败，未删减检查条件。
