# Windows 启动依赖与交接核查

> 历史发布记录；镜像、测试与“当前/最新”均指记录当时。 当前入口见[业务说明](../../business/README.md)与[运维指南](../../guides/operations.md)。

用户在 0.1.26 上仍报告需要先出现官方 BOSS 界面，工作台才可能启动。此前的离线 CI 通过不能代替这次真实机器结果。

## 代码中确认的架构

`windows_entry.py` 启动包内原 EXE 的 Node 控制器，控制器再启动原生 GUI 子进程。`integrated-shell.cjs` 把侧栏、顶栏和系统 BrowserView 装入原生 login/main BrowserWindow。界面位于同一窗口，但运行时仍依赖原客户端，入口和控制器也会继续存活。没有使用机器上另装的官方程序作为正常启动前提。

因此多个进程本身不证明存在两个独立界面；原生宿主退出后，工作台不能继续工作。这轮修复不将其描述为完全脱离原客户端的独立实现。

## 确认的启动缺口

1. 旧入口只用顶层 Chromium HWND 放行 inspector 激活；控制器随后只等 `$socket.handleEvent`，就开始查找原生模块。窗口名称、角色实例和 SDK 注册表仍可能没有建立。缺失与歧义均立即失败，且没有区分初始化进行中。
2. 正式启动从一次 inspector evaluation 中调度 `inspector.close()`，同时等待该 evaluation 的响应，存在先关闭通道再收到确认的竞争。旧整包自测在 inspector 仍连接时先交接窗口和运行 UI 检查，未走同一完成路径。
3. 正常运行中断也显示“启动未完成”，普通入口没有保留和自测同样的窗口观察结果。

## 调整

- HWND 仅用作允许迟激活的早期信号。正式接入前独立等待 Electron、dispatcher 和未销毁的 named login/main 窗口；不要求窗口可见、已登录或真实业务请求成功。
- 模块元数据缺失可在有界期限内继续只读观察，每轮释放句柄。歧义、传输丢失、安装器异常不重试；模块安装执行一次，不重放招聘动作。
- 入口确认安装成功后先断开 inspector，再写入当前 launchId/PID 的交接请求；原生进程关闭监听并以文件确认。正常启动与离线自测共用这条路径，自测在断开后执行。
- 整包验证主动触发一次原生窗口 SHOW，要求启动窗口确实拦住该窗口，再完成交接，补上上一轮 `nativeWindowsHeld:0` 的覆盖缺口。
- 普通启动保留有界阶段与窗口计数诊断，并区分启动失败与运行中断。
