## 实测

同一公司、全部财务店铺、2026-09-25 至 2026-10-24；列表每页 50 条。
以下是直接调用正式服务读取路径的时间，包含数据库查询、记录补充与成本汇总，
绕过总览的 Redis/进程响应缓存，不包含 HTTP 网络、登录及浏览器绘制。
数据库未清空缓存；同步持续运行，因此这些是实测样本，不是每次请求的时延保证。

| 查询 | 优化前 | 上线后 |
| --- | ---: | ---: |
| 总览 | 11,374 ms | 1,838 ms |
| 订单及成本汇总 | 9,226 ms | 1,101 ms |
| 结算明细及成本汇总 | 7,941 ms | 1,161 ms |
| 结算账单及成本汇总 | 3,337 ms | 1,426 ms |
| 退款及关联成本 | 超过 14 秒，被探针查询超时终止 | 148 ms |
| 对账及成本汇总 | 16,064 ms | 1,150 ms |
| 已结算订单成本页 | 4,411 ms | 1,901 ms |

订单页面请求不再重复读取总览已有的成本汇总。上线后的单次订单计数为 37 ms，
取第一页为 6 ms；上表仍保留带完整成本汇总的保守对比口径。

## 实现

- 将总览的店铺、每日、费用分类、订单状态四次范围扫描合并为一次覆盖索引汇总。
  Java 用 BigDecimal 按各维度重新汇总，再按原顺序换汇，保留未知金额、零值、
  负数、记录数及已知金额计数。导入的对比账单仍不计入平台账单图表。
- 公司内可见店铺集合只物化一次，保留公司、店铺、平台、日期、分组及币种边界。
- V130 添加公司/类型/日期分页索引及已结算订单关联覆盖索引。
  订单计数实测仍会误选旧用户前缀索引，故明确使用公司/类型/日期索引。
- 订单成本页面复用同一去重关系的汇总计数，取消额外的完整计数扫描。
- 在币种和人民币汇率快照已确定时，并行读取总览与明细；首次隐式币种仍先解析，
  避免表格与统计混用币种。仅允许复用相同口径的成本汇总，退款、结算、账单、
  待结算仍有各自口径。
- 图表资源下载不阻塞表格；旧内容在加载期间保留，并检查请求代次，
  防止晚到的记录或图表覆盖新的筛选。没有延长现有响应缓存的新鲜度窗口。

## 数据库配置与发布

部署前服务器可用内存约 23 GB，MySQL 无单独容器内存上限，原缓冲池 2 GiB。
相同汇总首次读取 2,789 ms，紧接着再次读取 583 ms；期间全局物理页读取增量
分别为 3,712 和 31（计数可能包含同步活动）。已用 `SET PERSIST` 将
`innodb_buffer_pool_size` 调为 4 GiB，确认调整完成且持久值一致。
如需独立回退该配置，可设回 `2147483648` 字节；应用回滚不自动回退数据库缓存。

索引通过 Flyway V130 执行 `ALGORITHM=INPLACE, LOCK=NONE`。首次因锁等待超时
未生效，确认两个索引均不存在后，只清理该次失败的 V130 历史项，并核对所有
既有成功迁移的校验和不变。等待当前任务结束、临时延后未领取的财务同步后，
成功执行 V130；原 next_at 恢复，未清除检查点或租约。

应用发布以当时的正式 JAR 为基础，只替换四个财务类族并添加 V130，
前端只替换 `index.html`、`finance-workspace.js` 及对应 gzip 文件。
已核对所有无关 JAR 条目、容器配置和其他服务容器保持不变。
数据库迁移与缓存调整均为附加变更，回滚应用时可保留。
