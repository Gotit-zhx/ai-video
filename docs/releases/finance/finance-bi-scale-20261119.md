# 财务 BI 投影追赶及大样本验收

2026-11-19，北京时间。关联[首轮九页基线](finance-bi-latency-20261119.md)。

## 线上只读采样

MySQL 8.4.11。统计信息估算累计账本约 1,037 万行、订单成本约 119 万行，登记 87 家店铺。9 月、10 月和 11 月的全公司、Shopee、TikTok Shop 共九个采样分区均有未完成的修订。10 月三种平台范围各有 31 个脏日，全公司账本投影正文约 44.6 MB。本阶段线上观察限于聚合形态和投影元数据。生产保持现行源码。现场已执行的 Flyway V160 与候选分支的历史 V160 文件编号冲突仍需按实际迁移历史处理。

## 改造

- 事件工作器先普通读取候选主键，再锁定具体事件。隔离试验在旧方式观察到插入事件与范围锁死锁。回归验证账本可在领取期间提交一整个事件批次，并确认晚提交事件保持可见性屏障，下一批能够消费。
- 构建工作器只在领取租约时读取标识和修订；投影正文在后续一致性快照里读取。连续脏日作为物理扫描区间，保留整月归属条件。满月修复执行一次原生整月重算，首日未受影响时保留部分月首日正文。仍按租约和所领取的修订原子发布，请求与构建修订一致且相关事件已经处理后，基线才对外可用。
- 结算明细与费用回退复用同一个快照中的原始条数，刷单等经营排除在原始明细里仍参与计数。结算账单、编号检索等保留各自精确路径。对账回退复用窄索引与单次币种查询，在对账页仅计算账单、商品成本、覆盖和筛选所用的数据。对账与费用首屏的投影轮询上限由 2 秒缩短为 250 毫秒。
- 回退请求按完整权限范围、筛选和视图收集 50 毫秒内的同条件并发请求，再共享一个只读快照。快照开始前关闭该批，随后到达的请求开始新批。结果不写入 Redis，个人字段设置仍逐个查询。
- 结算商品成本汇总复用按日期结算和按订单关联的已有索引。原首次结算和同日去重条件保持有效。

## 试验口径

压测数据由线上汇总形态生成，逐条财务记录均为合成。隔离环境为 MySQL 8.4、Redis 8、真实应用及 Chrome，Docker 可用 10 核与约 8 GiB 内存，隔离 MySQL buffer pool 为 2.5 GiB。主要范围为 2026 年 10 月整月，实时大屏查当天。合成夹具有 87 家店铺、约 159.8 万条账本、95 万条平台费用、30 万条结算明细、13 万条商品成本、24 万条贴单明细和 6.5 万条退件。样本覆盖一个重月的记录量，全历史索引、平台行为及生产数据分布存在差异。

两个场景每页分别采集 5 个并发样本，使用独立浏览器上下文，从已登录深链接导航到页面加载、主表或合法空状态和相应图表完成。每批清理该隔离公司 Redis 财务快照；MySQL buffer pool 和应用进程正常保留。持续写入场景每笔事务修改最多 8 条费用、4 条结算金额，分布于整月与多店铺。浏览器等待上限 25 秒，超时样本按观测下界计入失败。每页 5 个样本可用于判定本轮观测，样本量不足以证明线上尾延迟。

| 实时大屏 | 0.811 ✓ | 0.637 ✓ |
| 结算中心 | 8.961 | ≥25.000（5 次超时） |
| 对账中心 | 3.493 ✓ | 8.793 |
| 订单与退款 | 1.092 ✓ | 3.400 ✓ |

基线投影完整时 8/9 页通过。持续写入时 5/9 页通过。对账、订单和广告的完整响应标记为 PENDING，表示本次结果由账本快照计算。结算在两组均超预算。静态场景下结算走 READY 投影，耗时仍主要来自明细所需的首次结算成本汇总。新增请求合并前的同规模持续写入轮次中，总览、结算和费用均达到 25 秒超时，对账最慢 22.901 秒。合并后的总览、对账和费用在本次均完成，仍超出预算。

## 投影追赶

最终场景持续写入 84.61 秒，397 笔账本事务提交，共更新 4,661 行。前一轮独立压测另有 502 笔、5,895 行。两轮均在修复事件领取锁后执行，写入器没有报告错误。最终轮次全公司 10 月分区在持续写入期间出现 31 个待补算日，采样最大修订差为 74，待处理事件最多 142 个。停止写入约 61.3 秒后，构建和请求修订一致（963），待补算日和事件数均为 0，连续写入期间仍存在投影发布延迟。停止写入后，10 月 Shopee 和 TikTok Shop 也观察到请求与构建修订一致。

页面瓶颈分成两处。结算即使读到 READY 投影，首屏仍要计算首次结算的商品成本。持续跨整月写入时，现有整月投影重算及权威回退仍要多次分段扫描；总览、结算、对账和费用本轮超过 5 秒。后续若把投影进一步拆成可独立发布的日或店铺事实，须同时处理跨日的首次结算、按账单发生日重分配、人工归属月和晚提交事件。

## 复跑入口

在本工作区创建全新隔离开发实例，使用 `python3 scripts/qa/seed-finance-bi-scale.py` 生成账本，再使用同一脚本的 `--details` 加载贴单与退件。两次种数均可通过 `FINANCE_BI_MONTH=2026-10` 固定月份，缺省使用上个月。从 Playwright 计时器读取环境中已有私有开发登录配置。冷 Redis 测试需要本工作区的 Compose 实例。

```sh
FINANCE_BI_BASE_URL=http://localhost:18087 \
FINANCE_BI_LOGIN_FILE=.env.development \
FINANCE_BI_MONTH=2026-10 FINANCE_BI_SAMPLES=5 \
FINANCE_BI_CONCURRENCY=5 FINANCE_BI_COLD_REDIS=1 \
FINANCE_BI_TIMEOUT_MS=25000 node scripts/qa/test-finance-bi-latency.mjs
```

持续写入时，同期在该合成数据库内每约 200 毫秒提交一组金额修订，以确定性编号跨店跨日期选择费用、结算各 8、4 条记录。运行期约每 1.5 秒观察全公司月份分区的请求和构建修订、失败计数、快照年龄、脏日及待处理事件，停止写入后继续观察至修订及队列收敛。隔离工作区 `.dev/finance-scale/coalesced/` 留存只含计时、路由、状态码、样本数量和投影水位的原始 JSONL。
