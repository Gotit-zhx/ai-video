# 财务订单成本待补齐筛选

> 历史发布记录；镜像、测试与“当前/最新”均指记录当时。 当前入口见[业务说明](../../business/README.md)与[运维指南](../../guides/operations.md)。

版本：`finance-pending-costs-20261026`

## 修改

- 订单成本页增加“全部订单 / 待补齐”按钮。筛选在服务端分页前执行，包含缺少订单、缺少成本快照、成本不完整及后台重算中的订单。
- Excel 导出接收相同 `costStatus`，只导出当前筛选范围的全部分页；汇总说明明确成本状态。
- 列表展示成本缺失原因，无订单记录时使用店铺及订单编号作为增量渲染标识。
- SKU 关联页在最近 2000 笔订单样本之外，补入历史已结算订单的缺失规格，展示影响订单数及原因。最多补充 1000 个独立规格，超出时提示，不把抽样关联完整解释为全部历史成本完整。
- 公司和用户分别保存本标签页的财务筛选。显式选择的日期刷新后保留；实时大屏使用独立日期，返回报表恢复之前的选择；退出登录清除已使用的筛选缓存。汇率快照不持久化。

## 验证

- 5 项前端脚本通过：待补齐筛选、筛选保留、成本操作、查询响应保护、利润展示。
- 109 项后端测试通过，包括服务器临时 MySQL schema 中的集成测试；测试账户和 schema 已移除。
- 集成覆盖 50 条分页边界、缺少原订单、缺少快照、重算队列、取消订单排除、公司及日期隔离、Excel 范围一致，以及最近 2000 笔之外的历史规格。
- 明确确认规格映射后，通过现有成本队列重算历史订单的流程已验证。
- 生产只读核对覆盖 6 页待补齐订单、导出数量、历史规格返回和历史账本合计；使用临时 SELECT-only 账户。
- 发布仅覆盖 4 个后端类族和 4 个前端文件；其余 JAR 内容、数据库结构、服务配置及同步计划保持原样，前端普通及 gzip 资源均校验。

## 数据边界

本次发布不猜测普通款、升级款或赠品的成本关系，不修改原平台订单、成本单价、结算或平台费用金额。

所排查的历史订单商家 SKU 为空，官方商品及规格接口仍返回正常状态，因此不能归因为下架。普通款与升级款在成本表中同时存在；旧规格展示名称已变化，无法据此确定实际发货型号。只有确认实际成本型号及单位后，才能保存关联并批量补齐这些订单。缺失成本继续留空，不按零计算利润。
