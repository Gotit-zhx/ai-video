# 商家 SKU 商品标准成本

## 行为

- 商家 SKU 是成本匹配依据。中英文外层括号、空格和乘号可规范化匹配；销售规格文字不否决型号关联。人工关系按店铺和分组隔离并优先使用。
- 标准成本为人民币单价 × 购买数量 × 组合数量。完整组合装成本优先且系数为 1，没有完整组合装价格时才使用唯一基础型号及编码中的数量。
- 成本仓优先店铺配置，否则按国家唯一匹配海外仓。默认下单月份取价，缺价采用最近更早月份并明确显示历史价估算；可配置为不估算。零值、歧义仓库、缺型号、缺数量不视为零成本。
- TikTok 按唯一商品行 ID 计量并去重，显式数量优先；Shopee 使用购买数量字段。TikTok 商品行状态读取 `display_status`，部分取消与其他商品发货分开处理。退款不自动冲回商品成本。
- 总览、订单、退款、结算明细、结算账单、待结算、对账、平台费用、广告及实时大屏展示商品成本；分组与店铺汇总沿用当前筛选条件。手工费用台账保持独立来源。
- 退款、结算和账单先关联订单再去重汇总；单行的完整关联订单成本不可直接跨行累加。商品成本不写入外部费用 `COST`，不修改平台结算净额或对账差额，不把不同业务日期的收入和成本相减称为净利润。
- 成本管理新增订单成本、待补齐数量、历史价数量和计算明细。刷新保留原节点，数据未变化时不更新结果 DOM。

## 后台与数据

V128 增加 `finance_order_costs`、`finance_order_cost_jobs`、`finance_cost_rebuilds`，以及历史游标、订单关联、账单关联三个索引。

订单与计算任务在同一业务事务保存，规范化源数据哈希用于避免无变化的重复工作。后台使用独立线程，每轮填充最多 500 笔历史任务，处理四批、每批 50 笔；实时新订单优先。失败事务回滚保留队列，历史游标可续跑。

成本设置、成本表、人工关系、店铺分组或时区变化触发重算。结果变动写入审计记录；页面只读取快照，不扫描全部原始订单 JSON。缺少资料时显示已计算部分，完整合计为空。成本金额始终为 CNY，不随展示币种二次换算。

## 发布维护

本次初次部署遇到 Docker overlay 挂载参数超长，已由发布脚本恢复原运行镜像和同步计划。旧镜像后端 128 层、前端 469 层。

`scripts/release-finance-costs-flatten-retry.py` 仅在当前容器仍为已验证回退版本时使用：导出现有根文件、加入本次文件、重新构建少量层镜像，逐项验证运行元数据。仅 Ubuntu 描述标签的换行转为空格，运行配置保持一致。不会删除数据卷或清理其他镜像。

重建后后端 2 层、前端 9 层，镜像大小分别约 413 MB、49 MB；旧镜像保留用于回退，不将镜像逻辑大小减少等同于已回收磁盘空间。生产结果验收使用只读检查器核对每条快照乘法、订单合计、缺价原因及各模块去重统计。

## 线上验收结果

- 正式运行镜像为 `finance-order-costs-20261023-flat`，V128、三个新表、三个索引、前端原始文件及 gzip 文件均校验通过，匿名财务请求仍返回 401。
- 已配置成本表店铺的 10,216 笔订单全部生成快照，历史回补为 `DONE`，队列为 0。7,402 笔使用对应月份价格，2,233 笔使用标记清楚的历史价格，581 笔未付款或未发货取消订单不计成本。
- 全量复核 11,205 条已计价商品行的乘法和订单合计，通过；未发现缺成本问题。订单、退款、结算、账单、待结算及对账六种口径的待补齐数量均为 0。
- 该店铺所选月份的服务端成本汇总查询实测约 13–118 毫秒，50 行订单明细读取及成本补充约 204 毫秒；这是服务端样本耗时，不是浏览器端到端延迟。
- 后台没有记录成本批次失败。没有成本表的其他店铺仍显示待补齐，不能据此宣称全公司所有商品均已具备成本。
