# 订单同步死锁修复

2026-10-30 线上订单同步出现 SQL 错误。InnoDB 死锁报告确认：两个同步事务都持有 `finance_label_state` 同一行的共享锁，随后在增加贴单匹配版本时申请排他锁，形成锁升级死锁。

共享锁来自成本队列的 `INSERT ... SELECT`：MySQL 默认隔离下会锁定其读取的来源行。两个事务的订单不同，但贴单状态属于同一公司，因此撞到同一行。

## 修复

- 成本队列先用普通一致性读判断是否需要计算，再使用 `INSERT ... VALUES ... ON DUPLICATE KEY UPDATE` 写入。队列唯一主键继续防止重复，同步写入不再因此持有贴单状态共享锁。
- 单条订单保存遇到悲观锁错误时，整笔事务回滚后最多尝试三次，重试之间有短随机退避。只重试本方法拥有的事务，调用者已有事务或线程中断时立即交回处理。
- 不重试第三方写操作，不清除订单分页断点，不改订单金额和日期口径。
- 发布后只将本次两类 SQL 错误的订单通道提前到期重试；保留原断点、错误记录及失败次数，直到真实同步成功才由原流程清除错误。

## 回归

- 在一次性 MySQL 库中，通过两路并发在成本入队后同时唤醒贴单匹配，旧版稳定复现线上死锁。
- 相同测试在新版通过，两个订单及待计算任务各写入一次，随后正确绑定原贴单费用。
- 验证第一次事务失败后的写入被回滚；第二次保存仅产生一条订单。嵌套事务不会在已失败事务内自行重试。
- 本次精确线上 JAR 覆盖版本的全部 12 项贴单集成回归通过，测试库和账号已清理。
