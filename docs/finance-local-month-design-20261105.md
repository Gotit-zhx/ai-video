日期：2026-11-05。状态：日期查询契约、整月入口、显示／导出说明和缓存版本已上线；未改变已有账单日期或金额。TK 本土店日期映射及 Shopee 独立 Adjustment 仍未完成，不能把本次发布称作整份方案全部验收。发布及空间优化凭据见 `docs/finance-local-month-release-20261105.md`。

## 用户看到的日期

用户继续用中文选择日期，例如“2026年10月”。这个选择明确表示每家店铺当地的10月。

页面筛选旁固定说明：“统计日期按店铺当地时间；同步时间按北京时间显示。”

- 单店查询：使用该店铺已确认的业务时区。
- 分组、全部店铺查询：逐店计算本地月份，再汇总结果。不同币种分开保留原币。
- 结算明细显示“结算日期（店铺当地）”；更新时间、任务开始及结束时间按北京时间显示。
- 详情可显示同一原始时间戳的当地时间及北京时间。单纯的官方报表日期是日历日期，不能先虚构午夜时间戳再换算。
- 不因用户电脑时区、浏览器语言、服务器时区改变统计结果。
- 首版不增加默认“统一北京时间统计”切换，避免用户无意切换口径。若将来需要统一时刻区间分析，另列报表，不能命名为官方当地月报。

例如选择2026年10月：

| 店铺 | 当地统计范围，左闭右开 | 同一范围换成北京时间 |
| --- | --- | --- |
| 菲律宾／马来西亚 UTC+8 | 10月1日00:00至11月1日00:00 | 10月1日00:00至11月1日00:00 |
| 泰国／越南 UTC+7 | 10月1日00:00至11月1日00:00 | 10月1日01:00至11月1日01:00 |

使用已确认的店铺 IANA 时区。不能给全部店铺固定加减小时，也不能把每家店同一个月的选择先转换成统一的北京时间区间。

## 分开保存和使用业务日期

| 业务事实 | 统计用途 | 禁止替代 |
| --- | --- | --- |
| 订单创建时间 | 查原始订单、订单数量及创建月 | 不替代结算日 |
| 官方报表结算日期 | 收入、净结算、平台费用及结算明细月报 | 不自动替换为付款日或千易收货日 |
| 实际放款／付款时间 | 资金放款、付款对账；Shopee Income 按其官方释放规则 | 不代表所有平台的报表结算日期 |
| 独立调整完成日期／所属账单日期 | 后续退款、赔偿、费用调整的发生期 | 不强行归入原订单创建月或首次放款月 |
| 千易实际 receiveTime | 千易退货收货统计，沿用已确认的北京时间口径 | 不替代平台结算日期，不使用 finishTime/updateTime |

保留原始平台时间戳、字段来源、交易编号及原币金额。报表日期的推导规则记录适用平台、地区、店铺类型、时区和版本。日期口径升级不能改造出一笔金额补差。

## 两个平台的适配

### Shopee

1. Released 收入按实际放款日期筛选，使用 actual_payout_time 和 released_amount。
2. 按店铺当地完整自然月规划窗口，并按接口允许的窗口长度拆分。
3. Income 与 Adjustment 分别入账、分别核对。调整使用独立事件及完成日期，关联原订单但不覆盖原订单已经验证的释放金额。
4. 不能把 escrow 累计调整后的余额重新当作当月放款，也不能将一条调整同时计入 Income 和 Adjustment。
5. 销售收入、费用、释放金额分别对照官方相应栏目，不用净放款冒充销售收入。
6. 官方报表生成／下载接口可作为独立核对途径，但要先确认目标店铺权限、返回格式及它与目标明细导出的对应关系；文档里的 PDF 示例不能直接视为用户现有 Excel 的同版文件。

### TikTok Shop

1. 保留 statement_time、payment_time、payment_status、statement_id、payment_id，各自含义不合并。
2. 结算月报对齐对应导出中的 Statement Date，付款对账对齐对应付款字段。
3. 当前代码固定将 statement_time 的 UTC 日期加一天。不能将它继续当成全部店铺通用规则，也不能未经验证把全部店铺切换至 payment_time。
4. 日期规则分别验证本土店和跨境店，并覆盖普通账单、负数账单、调整账单及月初月末。店铺类型是验证维度，不是仅凭两例即可写死的算法。
5. 抓取账单时使用官方支持的 statement_time 生成时间区间。该区间与目标报表日期不一致时，按已验证映射覆盖相邻账单窗口，再按目标报表日期归属；不把 API 请求窗口当作最终入账月份。
6. 收入使用原始 revenue_amount，净结算使用 settlement_amount，折扣及退款不能再次重复扣减。费用及调整保留原始正负号。
7. 同一订单可能存在多条结算、退款或调整交易。以平台交易身份去重，不以“每个订单只留一条”去重。
8. 结算是否计入必须匹配目标官方报表定义。付款状态独立展示，不能把银行尚未到账直接推断成所有结算报表均不应计入。

## 抓取完整性

- 保留原有历史、分页、账单明细断点，人工立即同步优先，上月缺失数据优先。
- API 页必须全部成功；有下一页游标就继续，失败保留原位，重试受既有限流和退避约束。
- 每个账单的明细数量／金额与平台返回的控制信息核对。只能在明细完整后把该账单标记为完整。
- 原始订单查找与已结算财务分开。尚未结算订单可以查到，但不能提前算作已结算收入。
- 完成初次整月抓取后，利用更新游标及有界重叠窗口刷新迟到的结算、退款和调整；根据真实更新记录失效相关店铺月份缓存。不能每次从整月第一页重抓。
- 重复请求保持幂等；调整、退款、负数流水与不同次结算不得被误删。
- 抓取完整与官方对账通过是两个独立状态。没有原始官方文件独立核对时，只能表明接口抓取完整。

## 官方验收

先建立四种典型样例：Shopee 菲律宾、Shopee 泰国、TikTok 本土、TikTok 跨境；有官方原文件的先验收，缺失样例不能伪称通过。

对相同店铺、月份、报表类型、时区、币种：

1. 检查完整交易集合的缺失、额外及重复，不能只比较订单数或总额。
2. 对照账单编号、订单／调整编号、交易类型、所属日期、币种及金额。
3. 官方按SKU拆行、API按交易／订单拆行时，先对齐汇总层级，保留所有有效拆行。
4. 分别核对收入、平台费用、调整和净结算。差额必须能定位到具体账单／交易及日期，不允许人为补差。
5. 检查上月最后一日和次月第一日，测试泰国本地月末23:30等跨北京时间月份的记录。
6. 检查列表、页尾合计、总览、趋势、分组汇总、单店及全部店铺导出使用同一日期规则版本。
7. 官方流水对账保留完整交易。运营利润的既有刷单排除另行呈现，不能将排除后的利润统计直接拿来宣称与官方完整流水一致。

已确认的样例边界：

- Shopee 菲律宾2026年10月 Income 曾逐单验收5577单；独立 Adjustment 不能据此宣称已验收。
- TikTok YUXI 3PF1 PH 跨境店2026年9月，本次重新按账单编号核对30笔，日期、收入和净结算与现存记录一致。其报表结算日期全部比当地付款日晚一天。
- TikTok ATC 本土店2026年10月，按当地付款日得到的收入和净结算与截图合计一致，但尚无原始文件做逐交易验收。
- 两个TikTok样例均为Asia/Manila、PHP，差异不能仅归结为中国与当地时差。

## 查询速度、缓存及磁盘

- 同一查询复用一个后台任务。前端等待现有任务结果，不不断创建新查询或机械重试。
- 缓存包含公司及数据权限、选中店铺集合、日期范围、日期口径版本、币种和已应用的数据版本。组别筛选先解析有效店铺集合。
- 当数据或日期映射变化时，只失效受影响店铺及月份的缓存。旧缓存如用于展示必须明确更新时间，不能伪装成新口径结果。
- 稳定历史月份复用汇总；当前／上月根据真实数据更新刷新。列表和导出读取一致的已应用版本，避免一部分旧日期、一部分新日期。
- 优先复用原始JSON中的时间证据及既有联合索引。必要日期映射放在较小的账单级结构，不复制整份财务明细。
- 先验证查询计划和实际耗时，再决定索引；不得在当前磁盘条件下盲目重建大型 finance_records 表或重复建宽索引。
- 不增加持久化诊断日志，不生成长期重复快照。核对只保留必要的小型验收记录。
