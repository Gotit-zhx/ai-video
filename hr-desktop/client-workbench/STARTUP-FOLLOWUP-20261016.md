# 2026-10-16：启动可靠性与 Windows 验证

## 直连服务启动

本地用真实子进程管道复现：主进程同步阻塞超过启动时限时，子进程已经输出就绪握手，旧实现仍先执行超时回调并终止子进程。超时终止后的 `exitCode` 为 `null`、`signalCode` 为 `SIGTERM`；旧清理再次等待已经触发的 `close` 事件，无法结束。

修复让超时判断先让出一轮 I/O，读取已经到达的握手；没有握手仍按原时限失败。清理识别已经按信号退出的子进程。失败记录保留最后初始化阶段，不保存账号、凭据或原始错误内容。未放宽网络回退、登录、风控或请求限制。

该缺陷已确定性复现，但 r30 首次 GUI 失败没有保存失败前阶段，不能据此断言当时必定是同一原因。

验证：339 项 Node 回归通过，24 项打包/导出 Python 检查通过；原 Electron 22.3.24 / Node 16.17.1 中独立执行管道阻塞、真实超时和信号退出清理检查通过。Node 16 自带实验性 test runner 缺少 `t.after`，因此原环境验证使用独立脚本；没有将测试框架不兼容当作通过。

## Windows

此前原生探测错误地要求匿名原客户端旧 `_sdk_chatSocket_sendTextMessage` 必须完成编码。当前产品文本和求简历使用 `WindowsAdapter -> NativeChat`。保留旧 SDK 的缺少身份拒绝诊断，不注入原客户端身份。

新增整包要求：真实 Windows 适配器进入隔离 Electron 页面夹具，验证精确职位、一次动作和真正匹配的夹具回执；旧发送器与网络调用必须为零。缺少适配器路径证明的候选包不允许导出。该测试仍是合成夹具，不能代表真实 BOSS 账号验收。

独立调试端口探测仍保留失败门禁，并新增仅固定分类的启动诊断：失败阶段、激活是否完成、退出码、端口冲突、参数错误和字节码拒绝。没有改连其他进程或关闭其端口。

Windows 原运行时的新检查和完整实机业务结果待验证，不声明双端整体完成。
