# 原客户端改造实验

目标：沿用用户提供的 BOSS 原客户端扫码登录、真实会话和消息接收，增加赫逸工作台。实验产物使用单独的名称、App ID 和数据目录。

Mac 使用已审核的 `1.7.4 / ARM64` 输入，保留原认证和登录窗口。Windows `1.7.5` 安装器与主程序实际都是 x86；已完成指定资源的认证读取，`main.jsc` 仍为 V8 字节码，Windows 改造应用尚未构建。

## 当前实现和验证

- Mac 原客户端登录窗口可以启动，扫码登录、手机登录与协议控件已渲染。2026-10-15 在 r3 实际窗口观察到已登录的 BOSS 消息页面；未据此判定助手业务链路已经通过。

- 原生页面、官网视图与原客户端代理服务使用同一个网卡中继；不可切回系统代理。当前检查覆盖会话代理配置及失败停止，不能据此认定所有原生 socket 路径已经审计。
- 登录区域支持 Mac ⌘V、Windows Ctrl+V 与输入框右键粘贴；Windows 实际运行仍待验证。
- 隐藏下载窗口沿用原客户端针对认证代理的 HTTPS 初始化路径，避免新中继配置与旧代理设置不一致时二维码下载失败。r6 隔离 UI 检查已确认二维码实际加载、仅一个可见窗口及默认会话指向网卡中继；没有真实扫码或发送消息。
- 赫逸入口使用已有租约授权和用户隔离；原客户端的用户 ID 需要与绑定账号一致。
- 原客户端接收回调进入活动队列，不额外创建消息订阅或轮询。
- 文本发送等待候选人、账号和 `clientMid` 一致的消息回执。超时保持未确认，不自动重复发送。
- 现有 SDK 请求保护继续包围原生传输：额度记账、Cookie 校验、职位核对和风险停止已通过离线测试。

- 普通登录过期仅在原客户端完成同一账号的真实重新登录后解除本地过期标记，随后仍需助手明确验证。账号风控、认证要求和重复登录限制不会被这一入口清除。

## 构建 Mac 实验产物

在 `client-workbench` 目录安装独立依赖：

```sh
pnpm install --ignore-workspace --ignore-scripts
```

使用项目已有 Python 环境构建 `hr-desktop/runtime/build.py`。随后：

```sh
python build_mac.py \
  --source-app "/Volumes/BOSS直聘 1/BOSS直聘.app" \
  --output-app "/Users/heyi/Applications/赫逸工作台-改造测试版.app" \
  --sdk-endpoints "/absolute/path/to/boss_agent_cli/api/recruiter.yaml"
```

构建器核对原 `main.js` 的 SHA-256，保留有效的 ASAR 文件和原生模块，跳过目录中超出容器范围的异常条目。认证逻辑和原生可执行文件不被补丁修改。改造应用使用本地 ad-hoc 签名，不能沿用厂商签名。内部 `CFBundleName` 保留，以兼容 Electron 22 查找原 helper 的规则；外部名称和 App ID 明确区分实验版。

`build_mac.py` 拒绝覆盖现有应用。第三方文件和派生产物在仓库外；不要将它们提交或发布到 Git。

## 离线验证

```sh
node --test *.test.cjs
```

原生 Python 适配测试需在独立进程运行，先用 `runtime/build.py --stage-only` 准备共享代码，然后在 `runtime` 目录执行 `PYTHONPATH=build/shared python -m unittest test_native_client -v`。它使用临时目录与合成数据，覆盖职位核对、额度记账及风险停止；不使用真实账号。

运行派生应用的 `--heyi-workbench-smoke` 时，必须同时提供新的 `HEYI_WORKBENCH_TEST_DATA` 和 `HEYI_WORKBENCH_TEST_OUTPUT`；测试只使用夹具，不运行原客户端登录。

`--heyi-workbench-ui-check` 使用原客户端启动路径，需要 `HEYI_WORKBENCH_TEST_PORT=0`，从而不占用稳定助手端口。它检查二维码实际加载、单个可见窗口及会话代理配置，会加载原登录页及其公共网络资源，不扫码或发送候选人消息。
可额外设置 `HEYI_WORKBENCH_TEST_LIVE_BRIDGE=health-only`，仅从隔离官网页面读取已经运行的 `17861/health`。此检查不配对、读取招聘账号或触发 BOSS 操作；报告将独立记录页面连接与二维码结果。

## Windows 静态分析

`inspect_windows.py` 读取 PE 布局、入口地址和固定加载标记。`NativeEntryProbe.java` 在 Ghidra 的只读导入中逐个反编译选定入口，限制函数与指令数量，不执行 EXE。输出的伪代码是机器码推断，不等于还原原始源码。

Rea 整个 Windows EXE 的自动分析达到 600 秒上限，随后使用同一 Ghidra 后端定向检查启动函数、ASAR 读取、KDF 与 AAD 构造。原资源采用 `bzl-aes-256-gcm-v2`。

`read_windows_asar.py` 对确切 EXE 指纹进行只读认证：校验原 manifest 的 Ed25519 签名、ASAR header、AES-GCM tag、文件及分块 SHA-256。实际认证导出 50 个选定文件，存于仓库外；未执行 EXE、修改 manifest 或输出密钥。15 个合成数据测试覆盖篡改、截断、越界、路径穿越及拒绝在 Git 工作区导出。

资源可读取不代表业务源码已恢复。`main.jsc` 仍是 V8 字节码，Windows 的适配、构建和真实执行验证仍未完成。
